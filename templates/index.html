policy.msc — How the work is judged

✓Proof over breadth.

A feature counts when its failure behaviour is tested and stored — CI regressions, a real HTTP testbed, and committed load runs.

✓Truthful states.

“Accepted” presented as “done” is the industry’s favourite bug. Publishes stay pending until probed live; unmeasured checks stay uncertain.

✓Kill it at any moment.

Crash tests have catalogue numbers (F01–F09). Bugs get a replayable seed: colophon-sim --seed N --trace.

✓Bounded everything.

Every queue, body, page, cache, retry loop and pool has a limit and a deadline — a bound you can’t name is an outage you haven’t met yet.

✓No AI hype.

Agents work through the same API and permissions as everyone else — draft-only, budgeted in Postgres, never self-approving.

404human.hlp — Asked plainly
Why build in the open, including the mistakes?

Because “proof over breadth” can’t be claimed, only shown. A build log that includes the failures is the difference between saying a system is reliable and letting you check.

Is any of this usable yet?

Colophon is pre-0.1; Service Monitor has an installed release; jsrt’s roadmap and hardened load runs are done; the seven newer projects are still early. Check the progress ledger for every project’s exact stage and open items.

Why Rust?

One type system for the error envelope, explicit deadlines on every I/O await, compilers that refuse what production would regret, and deterministic failure simulators.

How minimal is this site, really?

Zola generates it: one stylesheet, one small inline script for the theme toggle and ticker, no tracking, and one self-hosted font. Accordions are native <details>.
